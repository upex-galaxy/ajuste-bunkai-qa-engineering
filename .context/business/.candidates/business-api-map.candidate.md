## 1. Executive summary

This API is how a QA team turns a backlog into an executable, auditable test operation. Teams bring structure in (from Jira or by hand), author Acceptance Test Cases, assemble them into suites and release-scoped plans, execute runs, and publish verdicts and coverage — all through one versioned surface (`/api/v1`) that the product UI itself consumes. The business does not "call an API"; it performs QA operations, and every one of them lands here.

Three kinds of callers share the same surface: browsers on a session cookie (the product), scripts and CI/CD on personal access tokens, and inbound machine callers — Stripe webhooks and Vercel Cron — which authenticate with a signature or a shared secret instead of a user. One identity resolver folds cookie and token callers into the same principal, so authorization behaves identically no matter who knocks.

The business-critical edges are few and sharp: onboarding is gated on an email leaving Supabase Auth/Resend; revenue is gated on a signed Stripe webhook being accepted and de-duplicated; run verdicts feed the coverage numbers the business reports; and workspace export/deletion can move or destroy an entire tenant's data. Everything else is authoring CRUD sitting behind row-level security.

## 2. Permission & auth model

### Tiers

| Tier | Who it applies to | How to acquire | Where enforced (code path) |
|------|-------------------|----------------|----------------------------|
| **Public** | Anonymous visitors | None (signup, magic-link request, health, OpenAPI doc) | Route marked public; no `resolveIdentity()` call |
| **Session cookie** | Browser users of the product | Magic link (`POST /api/v1/auth/magic-link`) or signup, verified at `GET /auth/callback` | `middleware.ts` (edge: session refresh, route matcher) → `resolveIdentity()` in `lib/api/principal.ts:50` |
| **Bearer PAT** | Scripts, CI jobs, AI agents | `POST /api/v1/tokens` (cookie-authenticated); plaintext `bk_pat_<prefix>.<secret>` shown once, only SHA-256 stored | `lib/api/middleware/bearer.ts` (token-family lookup) → `resolveIdentity()` |
| **Cron secret** | Vercel Cron scheduler | `CRON_SECRET` env var sent as `Authorization: Bearer` | `isValidCronSecret()` in `app/api/v1/admin/send-digest/route.ts:41` (any-verb gate) |
| **Webhook signature** | Stripe (inbound) | `stripe-signature` header over raw body | `constructEventAsync()` in `app/api/v1/billing/webhook/route.ts:61` — the only auth on that route |

### Roles and capabilities

Workspace roles live in `workspace_members` and are enforced twice: in Postgres by RLS (`bunkai_user_role()` → `viewer / member / admin / owner`, `bunkai_is_workspace_admin()`), and in handlers by `requireCapability()` / `assertWorkspaceContext()` (`lib/api/principal.ts:84,96`). PATs carry a scope array (`atc:read`, `atc:write`, `run:execute`, `workspace:admin`) — but per-route scope enforcement is unverified and BK-117/BK-134 record that `workspace:admin` was self-issuable by members (see §7).

### Token flow — session cookie (primary scheme)

```
Browser                    Next.js API                      Supabase Auth
  │  POST /api/v1/auth/magic-link                            │
  ├────────────────────────────►│ signInWithOtp() ───────────►│
  │                             │◄── email out via Resend ────┤
  │  GET /auth/callback?token=  │                            │
  ├────────────────────────────►│ verifyOtp() ────────────────►│
  │◄── Set-Cookie sb-*-auth-token (refresh) ──┤               │
  │  (every later call)         │                            │
  ├────────────────────────────►│ middleware.ts refreshes ───►│
  │                             │ resolveIdentity() → Principal → RLS
```

### Token flow — personal access token

```
User / CI                  Next.js API                       Postgres
  │  POST /api/v1/tokens  (cookie auth)                      │
  ├─────────────────────────►│ SHA-256(secret) ──────────────►│ personal_access_tokens
  │◄── plaintext bk_pat_… (shown once) ──┤                   │
  │                                      │                   │
  │  GET /api/v1/atcs  Authorization: Bearer bk_pat_…        │
  ├─────────────────────────►│ bearer.ts: prefix + SHA-256 ──►│
  │                          │ resolveIdentity() → Principal (scopes attached)
```

No refresh token exists for PATs: revoke = delete the row. Cron and webhook tiers have no user principal at all — they gate a single route each.

## 3. Critical business journeys

Six journeys, selected by revenue → security → core value → blast radius. (The module-tree structuring flow from the previous baseline is folded into Journey 4 as an authoring prelude; decision logged in §7.)

### Journey 1: New QA team signs up and gets a workspace

**Purpose**: A QA engineer provisions an account and a first workspace in seconds — the front door to every other flow.

```
Browser                     API                          Supabase / Postgres
  │ POST /api/v1/auth/magic-link                           │
  ├─────────────────────────►│ signInWithOtp() ────────────►│ (email via Resend)
  │ GET /auth/callback ──────►│ verifyOtp() ────────────────►│ session cookie set
  │ POST /api/v1/workspaces  │                             │
  ├─────────────────────────►│ resolveIdentity()           │
  │                          ├─ bootstrap first workspace ─►│ workspaces + workspace_members
  │◄─────────────────────────┤ { workspace } → redirect /projects
```

1. User requests a magic link; Supabase Auth sends the OTP email (Resend underneath).
2. Callback verifies the token and sets the refresh cookie — the identity that every later call resolves.
3. First workspace creation bootstraps membership rows, so RLS has something to authorize against.
4. From here the user is a `viewer` until invited or promoted — membership is the unit of access.

**Endpoints**: `POST /api/v1/auth/magic-link`, `GET /auth/callback`, `POST /api/v1/workspaces` · **Entities**: `workspaces`, `workspace_members` · **Features**: FEAT-AUTH-001, FEAT-WS-001

**Why it matters**: If email delivery or bootstrap fails, nobody gets in — the entire system is gated behind workspace membership, and a silent Resend drop looks like "the product is down".

### Journey 2: QA lead invites a teammate with a role

**Purpose**: An admin expands the team with the right permission level — the main way authority propagates.

```
Admin                       API                          Postgres
  │ POST /workspaces/W/invites { email, role: member }     │
  ├─────────────────────────►│ resolveIdentity()           │
  │                          ├─ admin capability check ────►│ workspace_members (RLS)
  │                          ├─ uniqueness check (BK-60/61 gap)
  │                          ├─ token + hash ──────────────►│ workspace_invites
  │◄─────────────────────────┤ { invite, token, accept_url }│  (no email sent — copy-link)
  │  teammate: POST /invites/accept { token }              │
  ├─────────────────────────►│ verify hash ────────────────►│ workspace_members (role upsert)
```

1. Admin issues an invite; the API returns an `accept_url` — invite **email is not wired**, so sharing the link is manual (feature-map §9-2).
2. Acceptance exchanges the token for membership; role lands via upsert.
3. Known integrity bugs BK-60 (no uniqueness check against active members), BK-61 (duplicate invites), BK-62 (role overwrite) make this the weakest chain in the system.

**Endpoints**: `POST /api/v1/workspaces/[id]/invites`, `POST /api/v1/invites/accept` · **Entities**: `workspace_invites`, `workspace_members` · **Features**: FEAT-WS-002

**Why it matters**: Permission changes are a security-class flow; the invite chain currently relies on RLS alone while application-level checks are incomplete.

### Journey 3: Workspace upgrades its plan through Stripe Checkout

**Purpose**: The revenue path — a workspace buys the cloud plan, seats included, and the entitlement flips when Stripe confirms.

```
Admin              API / lib/billing/checkout.ts         Stripe            Postgres
  │ POST /workspaces/W/billing/checkout { plan, seats }  │                 │
  ├────────────────────────►│ INSERT open attempt ────────┼────────────────►│ billing_checkout_sessions
  │                          │ checkout.sessions.create ─►│                 │  (one open per workspace)
  │                          │◄── session id ─────────────┤                 │
  │                          ├─ backfill session id ──────┼────────────────►│
  │◄── { url } → redirect ──┤                             │                 │
  │  (user pays on Stripe-hosted page)                    │                 │
  │                                                       │ POST /billing/webhook
  │                                                       ├────────────────►│
  │                          │ signature verify (raw body)◄┤ stripe-signature│
  │                          ├─ event id fence ─────────────────────────────►│ stripe_webhook_events
  │                          │  (duplicate delivery → no-op)                │
  │                          ├─ activate plan / seats ─────────────────────►│ entitlement updated
```

1. Checkout attempt is inserted first (partial unique: one open session per workspace), then the Stripe session is created in `mode: 'subscription'` and its id backfilled.
2. Payment happens entirely on Stripe's hosted page — card data never touches this API.
3. The inbound webhook is the only route whose sole authentication is the Stripe signature over the raw body.
4. `stripe_webhook_events` (PK = Stripe event id) fences replays: a redelivered event is a no-op, a missed one never arrives (failure mode, not an error).
5. Cancel path closes the open attempt so a later checkout isn't blocked by the one-open-session constraint.

**Endpoints**: `POST /api/v1/workspaces/[id]/billing/checkout`, `POST /api/v1/billing/webhook`, `POST /api/v1/workspaces/[id]/billing/checkout/cancel` · **Entities**: `billing_checkout_sessions`, `stripe_webhook_events` · **Features**: FEAT-BILL-001, FEAT-BILL-002, FEAT-BILL-003

**Why it matters**: Revenue path with async settlement — webhook idempotency (FEAT-BILL-002) and seat-upgrade collisions (FEAT-BILL-003, SQLSTATE 45700) are the high-risk points; a lost event means a paid customer without entitlement.

### Journey 4: Engineer authors tests, executes a run, gets a verdict

**Purpose**: The core product loop — author ATCs, assemble suites and plans, run them, mark steps, finish with a verdict that rolls into coverage.

```
Engineer                API                                Postgres / RPCs
  │ POST /atcs { steps, assertions } ───────────►│ bunkai_create_atc ──►│ atcs + atc_steps + atc_assertions
  │ POST /tests  →  POST /test-plans/[id]/tests ─►│ (Idempotency-Key) ──►│ tests, test_plan_tests
  │ POST /runs { test_id, start_token } ─────────►│ bunkai_create_run ──►│ runs (+ run_atcs, run_steps snapshots)
  │ POST /runs/R/steps/S/mark { result } ────────►│ bunkai_mark_run_step►│ run_steps (pending-only guard)
  │ POST /runs/R/finish { passed|failed } ───────►│ bunkai_finish_run ──►│ leftover pending → skipped
  │                                              │                     │ coverage rollup + notify trigger
  │  (or: idle > 4 min → pg_cron sweep → aborted with via='sweep')
```

1. Authoring creates ATCs through SECURITY DEFINER RPCs — steps and assertions land in one transaction; optimistic `version` returns 409 on stale writes.
2. A run snapshots its ATCs and steps (`run_atcs`, `run_steps`): later edits to the library never rewrite run history.
3. Start is idempotent — 24h fence on `(test_id, start_token)` plus `Idempotency-Key` middleware — so a retried CI call cannot double-start.
4. Step marks are legal only from `pending`; finish forces leftovers to `skipped`, computes the verdict, and fires the activity/notification trigger.
5. Abandoned runs are reaped by the pg_cron sweep (`via='sweep'`, idle > 4 min) so the state machine always terminates.

**Endpoints**: `POST /api/v1/atcs`, `PATCH /api/v1/atcs/[id]`, `POST /api/v1/tests`, `POST /api/v1/test-plans/[id]/tests`, `POST /api/v1/runs`, `POST /api/v1/runs/[id]/steps/[stepId]/mark`, `POST /api/v1/runs/[id]/finish`, `POST /api/v1/runs/[id]/abort` · **Entities**: `atcs`, `atc_steps`, `atc_assertions`, `tests`, `test_plans`, `test_plan_tests`, `runs`, `run_atcs`, `run_steps` · **Features**: FEAT-ATC-001, FEAT-TEST-001, FEAT-TPLAN-001, FEAT-RUN-001, FEAT-RUN-002, FEAT-COV-001

**Why it matters**: This is the value proposition; a broken run chain or a stuck `running` row distorts every coverage number the business reports.

### Journey 5: Team imports its Jira backlog

**Purpose**: Migration onboarding — existing epics/issues become Bunkai user stories linked to modules, without manual re-entry.

```
Engineer              API                            Jira REST         Postgres
  │ POST /imports { project_id, jql }                │                  │
  ├────────────────────────►│ resolveIdentity()      │                  │
  │                          ├─ one active job/project check (BK-142)   │
  │                          ├─ INSERT ──────────────┼─────────────────►│ import_jobs (queued)
  │◄─────────────────────────┤ { import_job }        │                  │
  │  (deferred: Vercel after() worker)               │                  │
  │                          ├─ fetch issues ───────►│                  │
  │                          │◄── issues ────────────┤                  │
  │                          ├─ per-issue upsert: component → module ──►│ user_stories
  │  GET /imports/[id] ─────►│ status + counts + errors ───────────────►│ import_jobs
```

1. The request only enqueues: identity check, single-active-job fence, insert — response returns immediately.
2. A deferred `after()` worker pulls issues over Jira's REST API (raw fetch in `lib/jira`, no SDK) and upserts stories keyed by `external_id`.
3. Progress is polled; per-issue errors accumulate while the job still completes (partial import is accepted by design).

**Endpoints**: `POST /api/v1/imports`, `GET /api/v1/imports`, `GET /api/v1/imports/[id]` · **Entities**: `import_jobs`, `user_stories`, `modules` · **Features**: FEAT-JIRA-001 (Beta)

**Why it matters**: Import is the migration onboarding path; missing Jira credentials fail the whole job (BK-142 on staging) and the worker dies silently with the function if Vercel kills it mid-flight.

### Journey 6: Admin exports or deletes a workspace

**Purpose**: Data-egress and offboarding — pull a full tenant archive, or remove the tenant entirely with a recovery window.

```
Admin                   API / after() worker             Postgres / Storage
  │ POST /workspaces/W/data-export                       │
  ├─────────────────────────►│ INSERT ───────────────────►│ workspace_exports (queued)
  │◄── { export } ───────────┤                           │
  │  (deferred worker: build archive → upload)           │
  │                          ├───────────────────────────►│ Storage bucket workspace-exports
  │                          │ status running → completed (expires_at = +168h)
  │  GET .../data-export/download ─►│ verify + stream ───►│ expired → denied
  │ DELETE /workspaces/W ────►│ soft delete + purge ─────►│ members/projects … (restore window)
  │ POST /workspaces/W/restore ─►│ undo ──────────────────►│ rows restored
```

1. Export inserts a job row (which also writes an `activity_log` egress audit event) and builds the archive out-of-band.
2. Download works only while the 168-hour expiry holds; failures are terminal (`failed`, no auto-requeue — user must re-request).
3. Deletion is recoverable inside its restore window; past it, purge is final.

**Endpoints**: `POST /api/v1/workspaces/[id]/data-export`, `GET /api/v1/workspaces/[id]/data-export/download`, `DELETE /api/v1/workspaces/[id]`, `POST /api/v1/workspaces/[id]/restore` · **Entities**: `workspace_exports`, `activity_log`, `workspaces` · **Features**: FEAT-EXP-001, FEAT-WS-003

**Why it matters**: Highest blast radius in the system — irreversible data movement, and the audit trail is the only evidence anyone pulled the tenant archive.

## 4. Architecture behind the API

```
┌───────────────────────────────────────────────────────────────────────┐
│ Client                                                                  │
│   Browser (Next.js SSR + cookie)   Scripts/CI (PAT)   Stripe, Cron      │
└───────────────────────────────┬─────────────────────────────────────────┘
                                │  sb-*-auth-token cookie / bk_pat_* bearer /
                                │  stripe-signature / CRON_SECRET
┌───────────────────────────────▼─────────────────────────────────────────┐
│ Edge (Vercel / Next.js middleware.ts)                                   │
│   session refresh · route matcher · page-level redirects                │
└───────────────────────────────┬─────────────────────────────────────────┘
┌───────────────────────────────▼─────────────────────────────────────────┐
│ Handler shell — lib/api/handler.ts (withApiHandler)                     │
│   resolveIdentity() → Principal · ErrorEnvelope · request logging       │
│   lib/api/idempotency.ts — opt-in per route (5 routes today)            │
└───────────────────────────────┬─────────────────────────────────────────┘
┌───────────────────────────────▼─────────────────────────────────────────┐
│ Route handlers — app/api/v1/** (81 route.ts) + app/auth/**              │
│   lib/billing · lib/jira · lib/mail · lib/runs · lib/api/pat            │
│   deferred work: after() in imports + data-export                       │
└───────────────────────────────┬─────────────────────────────────────────┘
┌───────────────────────────────▼─────────────────────────────────────────┐
│ Supabase (Postgres + Auth)                     External boundary         │
│   RLS (bunkai_* helpers) · SECURITY DEFINER RPCs (bunkai_* / * _v1)     │
│   pg_cron: run sweep · daily digest     │   Stripe · Resend · Jira REST  │
└─────────────────────────────────────────────────────────────────────────┘
```

| Component | Role | Persistence / integrations touched | Why it matters for QA |
|-----------|------|------------------------------------|------------------------|
| `middleware.ts` (edge) | Session refresh, route matching, page redirects | Supabase Auth cookies | Matcher mistakes expose pages; stale sessions cause redirect loops |
| `withApiHandler` (`lib/api/handler.ts`) | Identity resolution, canonical error envelope, logging | — | Every handler inherits auth behavior here; a regression here is global |
| `resolveIdentity()` + `lib/api/middleware/bearer.ts` | Cookie vs PAT unification | `personal_access_tokens` | PAT regressions break all CLI/CI/agent workflows |
| Route handlers (`app/api/v1/**`, 81 files) | Business operations | via RPCs and direct writes | Per-route gaps: capability checks, scope enforcement |
| SECURITY DEFINER RPCs (`bunkai_create_run`, `bunkai_mark_run_step`, `bunkai_finish_run`, `bunkai_sweep_abandoned_runs`, `bunkai_create_atc`, …) | Escalated, transactional writes | Multiple tables at once | Bugs inside RPCs bypass RLS entirely — widest blast radius |
| RLS policies (`bunkai_user_role`, `bunkai_is_workspace_*`) | Per-row authorization | All tenant tables | Policy holes = cross-tenant privilege escalation (BK-117/BK-134 class) |
| `after()` workers (imports, data-export) | Deferred long work outside request cycle | Jira REST, Storage | Function kill mid-work = silent stuck jobs; no external queue |
| Vercel Cron + `CRON_SECRET` | Daily digest (`0 8 * * *` → `/api/v1/admin/send-digest`) | `notifications`, Resend | Wrong secret = 401 forever; wrong schedule = silent no-digest |

## 7. Discovery gaps

- **`.env.example` has no `STRIPE_*` or `CRON_SECRET` entries** — where webhook signing secret and cron secret are configured could not be verified without reading the real `.env` (not done, by policy).
- **PAT scope enforcement per route**: scopes exist on the token (`atc:read|atc:write|run:execute|workspace:admin`) but no per-route scope check was located; BK-117/BK-134 record `workspace:admin` self-issue. Needs a dedicated audit.
- **OpenAPI path-level `security` declarations**: spec documents the schemes, but per-path `security` was not verified — auth requirements live in handler code, so spec-only consumers cannot tell a public route from a protected one.
- **Invite email**: no Resend call in the invite route (feature-map §9-2) — confirm planned vs intentionally copy-link-only before writing tests that expect an email.
- **`api/schemas/` sync is partial** — only 3 files present; full `bun run api:sync` not run this session, so baseline claim "auto-generated `*.types.ts`" is unproven for most surfaces.
- **Import progress is pull-only** — `GET /imports/[id]` described as "SSE-ready" elsewhere, but no SSE implementation verified.
