## Executive Summary

Bunkai is a **multi-tenant Test Management System (TMS)** for QA teams. A workspace is the tenant boundary; inside it, projects hold a self-referential **module tree** (max depth 6) whose leaves carry **user stories** → **acceptance criteria (ACs)** → **automated test cases (ATCs)**. ATCs are the system's central artifact: UI/API/Unit layers, an execution **technique** and a **priority**, an ordered step/assertion model, and tags (max 10). A second artifact family — **tests** — chains existing ATCs into ordered, versioned suites that are what actually gets executed as **runs**.

Execution and quality tracking form the second pillar: a **run** snapshots a test's chain into immutable `run_atcs`/`run_steps` rows, progresses through step verdicts, and terminates as `passed|failed|aborted`. Failures become **bugs** (severity P1–P4, forward-only lifecycle) whose provenance rows (`run_id`, `run_step_id`, `atc_id`) are frozen at filing time but `SET NULL` on upstream deletion. Everything that matters is captured in an append-only **activity log**, whose AFTER INSERT triggers fan out into a per-recipient **notifications** inbox (in-app, 90-day visibility, idempotent per source event), plus a daily 08:00 UTC **email digest** claimed through `notification_digest_log`.

Commercial and lifecycle concerns complete the picture: **Stripe** checkout upgrades a workspace to the `cloud` plan (project limits 3 → 50, seat metadata in `purchased_seats`), **workspace exports** build archives into Supabase Storage with a 168-hour expiry, and **workspace deletion** follows a 30-day soft-delete grace with restore, followed by a nightly pg_cron purge that leaves a `workspace_deletions` tombstone outliving the tenant row. Auth is dual-mode — browser session and PAT both collapse to a single `Principal` for RLS- and Postgres-enforced authorization — but PAT issuance remains browser-session-only.

| Entity | Business Role | Why it exists |
|---|---|---|
| `auth.users` | Identity (Supabase Auth) | Password + email-verification sign-up; phone auth disabled. Single identity feeding browser sessions AND PAT issuance. |
| `workspaces` | Multi-tenant boundary + commercial unit | Carries the paid plan (`community|cloud|enterprise`), purchased seat count, and `deleted_at` grace clock. Everything below is scoped to it. |
| `workspace_members` | RBAC membership (`viewer\|member\|admin\|owner`) | Who can see/do what inside a tenant; the owner's last-member exit is blocked. |
| `workspace_invites` | Pending membership with 7-day TTL | Roles `viewer\|member\|admin` only — ownership is transferred, never invited (BK decision). |
| `projects` | System-under-test container | Bounded per plan by a DB trigger (3 community / 50 cloud / unlimited enterprise, SQLSTATE 45700) — limits live in Postgres, not app code. |
| `modules` | Hierarchical taxonomy of the product | Self-referential tree, max depth 6, materialized path, `archived_at` soft delete. Every testable artifact hangs off a leaf. |
| `user_stories` | Business requirement unit | `draft → ready_to_test` gate: needs ≥1 active AC. Soft-archiveable. |
| `acceptance_criteria` | Testable condition of a story | Positioned list; archiving the last AC auto-reverts the story to `draft` (DB trigger). |
| `atcs` | **CORE artifact** — one automated test case | Layer (`UI\|API\|Unit`) + technique + priority (0087) + tags (≤10) + `version` optimistic lock + tsv search. Note: `atcs.status` exists (CHECK pass\|fail\|blocked\|skipped\|running\|unrun) but is a **dead column** — no production writer; live verdicts come from `run_atcs`. |
| `atc_steps` / `atc_assertions` | Ordered executable detail of an ATC | Steps and assertions are separate ordered lists; assertions are what a run step actually evaluates. |
| `atc_acceptance_criteria` | AC ↔ ATC traceability (M:N) | Feeds coverage/traceability reports — the "is this AC covered?" answer. |
| `tests` | Executable suite = ordered ATC chain | Workspace-scoped (not project-scoped): `version` optimistic lock (0026), `tags text[]` (0030), title 1–200. |
| `test_steps` | Position in a test's chain | `unique(test_id, position)`; FK to `atcs` is `RESTRICT` (cannot delete an ATC in use). **No `unique(test_id, atc_id)`** — the same ATC may appear twice in one test. |
| `project_environments` | Execution target (Staging/Production) | `unique(project_id, lower(name))`; seeded for projects existing at 0031 — **new projects get no environments automatically**. |
| `runs` | One execution of a test | Status `running\|passed\|failed\|aborted`, `via user\|sweep`, `abort_reason`, optional `module_id`; 24h idempotency on `(test_id, start_token)`. |
| `run_atcs` | Per-ATC snapshot + verdict inside a run | Realtime-published (`supabase_realtime`); verdict computed from its steps: pending → failed → blocked → passed → skipped-on-terminal. |
| `run_steps` | Per-step immutable snapshot + evidence | `pending\|passed\|failed\|blocked\|skipped`; content copied at run creation so later ATC edits never rewrite history. |
| `test_plans` / `test_plan_tests` | Named release-scoped test plan (M:N to tests) | `status open\|closed`, `unique(lower(name))`, DB `unique(test_plan_id, test_id)` backstops the Idempotency-Key middleware; SELECT-only RLS, all writes via ADR-0012 SECURITY DEFINER RPCs (no caller-supplied actor). |
| `bugs` | Defect record (TMS) | Severity `P1–P4`, status forward-only `open → in_progress → resolved → closed`; provenance (`run_id`, `run_step_id`, `atc_id`) frozen at filing (`ON DELETE SET NULL`), `module_id` always populated; title 5–200 trimmed, ≤10 evidence URLs; never archived (0061) — project only grows. |
| `milestones` | Project target-date marker | Name 1–100, optional description ≤500, `target_date` today…+5y (bounds checked only on change). **No status, no completion, no deletion** — deferred by design. |
| `activity_log` | Append-only audit trail | Source of truth for "who did what"; AFTER INSERT triggers fan out to notifications. Reads go through an allowlisted RPC (not raw table select). |
| `notifications` | Per-recipient in-app inbox | Payload snapshot, idempotent on `(source_event_id, recipient)`, 90-day read visibility; Realtime-published. |
| `notification_preferences` | Global opt-out per user | `event_type` (`run_lifecycle\|bug_lifecycle\|mentions`) × `channel` (`in_app\|email`); `mentions` is locked-on (always delivered); race-safe upsert (`WHERE` clause, 0062). |
| `notification_digest_log` | Email-digest claim ledger | One row per user per day (`pending → sent\|failed`) — the DB-side idempotency that stops double emails from cron retries. |
| `access_tokens` + `access_token_secrets` | Personal Access Token (PAT) for CLI/agent | Raw secret isolated in a companion table (0086); issuance only through a browser session (never API-token-authenticated); revoked on workspace deletion/member exit. |
| `billing_checkout_sessions` | One Stripe Checkout attempt | `target_plan ∈ ('cloud')`, `seat_quantity > 0`, partial unique **one open per workspace**, Stripe session id unique-but-nullable; RLS SELECT-owner-only (writes via service-role). |
| `stripe_webhook_events` | Webhook replay fence | PK = Stripe event id → duplicate deliveries become no-ops; no FKs; service-role only. |
| `workspace_exports` | Tenant data archive job | `queued\|running\|completed\|failed`, `expires_at = completed_at + 168h`; archive lands in Storage bucket `workspace-exports`. |
| `workspace_deletions` | Tombstone outliving the tenant | No status column: `purge_deadline`, `purged_at`, `member_count`, `row_count_digest`. RLS enabled with **zero policies** — only SECURITY DEFINER RPCs touch it. |
| `import_jobs` | Async Jira import unit | `queued\|running\|completed\|failed`; progress consumed by the UI poller. |
| `idempotency_keys` | HTTP retry safety | `pending\|succeeded\|failed`; keyed per workspace+route so a retried POST never double-applies. |
| `feature_flags` | Per-workspace feature toggles | Present in schema; **runtime usage untraced** (see Discovery Gaps). |
| `user_view_state` | Per-user UI preferences | Saves list views/expansions; write path verified only partially. |
| `magic_link_tokens` + secrets | Passwordless sign-in | Single-use, TTL-bound; companion secret table keeps the raw token out of the main row (0086). |

**Narrative.** The spine is `workspaces → projects → modules → user_stories → acceptance_criteria → atcs`, exactly as in the baseline — the module tree is the product's geography and every requirement/ATC/bug anchors to a module. Two structural updates since the baseline: (1) **execution detached from authoring** — `tests` (ATC chains) are workspace-scoped and `runs` snapshot into `run_atcs`/`run_steps`, so test history survives ATC edits (baseline had no run model at all); (2) **quality records became first-class** — `bugs` with frozen provenance, `activity_log`→`notifications` fan-out, and `milestones`/`test_plans` as planning objects. The commercial layer (`billing_checkout_sessions`, `purchased_seats`, plan-limit trigger) and the tenant lifecycle layer (`workspace_exports`, `workspace_deletions` + cron purge) bracket the tenant: one governs how much of it you may build, the other governs how it dies and what survives.

## Business Flows

> Every flow traces **User → API → Logic → DB → Response**. RPC names are the `bunkai_*` Postgres functions; route paths are `app/api/v1/**`.

### 1. Workspace Onboarding (signup + first workspace)

```
User -> POST /auth/signup -> Supabase Auth (email verification)
     -> (confirm) -> sign in -> session Principal
     -> POST /workspaces {name}
        -> RPC bunkai_bootstrap_workspace
           DB: INSERT workspace + owner row (role=owner) + default project
              + activity_log workspace.created
        -> 201 + workspace JSON -> UI redirects to first project
```

1. User signs up with email/password; Supabase Auth creates `auth.users` (phone disabled, email verification required).
2. Signed-in browser calls `POST /api/v1/auth/signup` / `signin` (or magic-link variants); the route returns a session-scoped client.
3. First workspace creation goes through `POST /api/v1/workspaces` → `bunkai_bootstrap_workspace` (SECURITY DEFINER, actor bound from session — ADR-0012: **no caller-supplied actor**).
4. In one transaction: workspace row (`plan=community`), the creator's `workspace_members` row as `owner`, a default project, and `activity_log workspace.created`.
5. Response carries the new workspace; UI activates it via `POST /me/active-workspace`.

**Business rules**
- Workspace name uniqueness/trim rules live in the RPC (not re-verified this session — see gaps).
- The bootstrap RPC must never accept a client-declared actor id — authenticated principal only.
- First member is always `owner`; ownership is transferred, never invited.

**Code paths**: `app/api/v1/auth/signup/route.ts`, `signin`, `magic-link`, `confirm`, `workspaces/route.ts`, `me/active-workspace/route.ts`.

### 2. Authentication & Authorization (dual mode → single Principal)

```
Browser: email/password | magic link -> Supabase session cookie ----+
                                                                    |
CLI/Agent: PAT (Authorization: Bearer) -> /me (session-only!       |
             issuance requires browser session)                    |
                                                                    v
   BOTH collapse to Principal {userId, workspaceId?, role}
        -> RLS-scoped Postgres client OR SECURITY DEFINER RPC
           (Postgres RLS enforces authz — app checks are advisory)
        -> response filtered by same RLS scope
```

1. Two entry modes: **browser session** (password / magic link) and **PAT** for CLI/agents.
2. Every request resolves to one `Principal`; the route layer never branches authz logic by mode.
3. Data access is either a directly RLS-scoped client (session policy path) or a SECURITY DEFINER RPC whose actor is derived server-side (PAT path) — ADR-0012.
4. Raw secrets (PAT, magic-link, invite tokens) live in `*_secrets` companion tables, revoked from the read-only QA DB role (0086).
5. PAT issuance exists **only** behind a browser session — a PAT cannot mint another PAT (privilege-escalation wall).

**Business rules**
- Authorization is enforced by Postgres (RLS + RPC actor binding); app-layer checks are defense in depth, not the source of truth.
- Non-disclosure rule P0002: error responses must not leak whether an email exists (check-email/resend endpoints return uniform responses).
- Leaving a workspace or deleting it revokes the member's PATs.

**Code paths**: `app/api/v1/me/route.ts`, `auth/*`, `tokens/route.ts` (+ `[id]`), middleware → `Principal` resolution, `lib/` auth helpers.

### 3. Jira Import

```
QA Engineer -> UI /imports -> POST /imports {jiraBaseUrl, email, apiToken, jql?}
   -> route validates + INSERT import_jobs(status=queued)
   -> Vercel after() background worker (fire-and-forget)
      -> pages Jira REST API (JQL)
      -> upserts user_stories + acceptance_criteria (module resolution by path)
      -> import_jobs: running -> completed|failed (progress cursor on each page)
   -> 202 + jobId; UI polls GET /imports/[id] until terminal
   -> activity_log import.completed|failed
```

1. QA pastes Jira credentials + JQL into the UI (`/imports` page) → `POST /api/v1/imports` creates an `import_jobs` row (`queued`) and returns `202 + jobId` immediately.
2. The heavy work runs in a Vercel **`after()`** background callback (`app/api/v1/imports/route.ts`) — HTTP response never waits for Jira paging.
3. The worker pages Jira's search API, maps issues → `user_stories` (with `acceptance_criteria` parsed from AC-shaped text), resolving target module by issue path/label rules.
4. Progress (cursor, counts) is written back per page; the UI polls `GET /api/v1/imports/[id]` until `completed|failed`.
5. Terminal state emits `activity_log import.completed|failed`.

**Business rules**
- Import is idempotent-ish per issue key (upsert) so a re-run doesn't duplicate stories.
- Failure mid-way leaves `failed` with partial data — no rollback of already-imported stories (business accepts partial import + re-run).
- Jira credentials are used transiently; never echoed back in responses.

**Code paths**: `app/api/v1/imports/route.ts` (+ `after()`), `app/api/v1/imports/[id]/route.ts`, `.context/SRS/api-contracts.yaml`.

### 4. ATC Authoring (create/update + classification + search)

```
QA Engineer -> UI /projects/{slug}/tests/... -> POST /atcs {title, layer, technique,
                                                     priority, tags[], steps[], assertions[]}
   -> POST /atcs -> RPC bunkai_create_atc
      DB: INSERT atcs (+ version=1, tags<=10 CHECK)
          INSERT atc_steps / atc_assertions (ordered, positions)
          M:N rows in atc_acceptance_criteria (AC binding)
          atcs_refresh_tsv trigger -> search_vector
          activity_log atc.created
   -> 201 + ATC JSON (with version)
Edit -> PATCH /atcs/[id] {version, ...}   <- If-Match optimistic lock
   -> RPC bunkai_update_atc: WHERE version=expected -> version+1
      (stale version -> 409 conflict, 453xx family)
```

1. Author picks layer (`UI|API|Unit`), technique, priority, tags (≤10), ordered steps and assertions, and binds ACs — one POST to `POST /api/v1/atcs`.
2. The RPC writes ATC + steps + assertions + AC-bindings transactionally; the `atcs_refresh_tsv` trigger maintains `search_vector` for title/tag search (`GET /atcs/search`).
3. Edits carry `version` (optimistic lock, 0026-style pattern): mismatch → `409`, business consequence: two editors can't silently clobber each other — the second one reloads.
4. Duplication (`POST /atcs/[id]/duplicate`-style route) copies steps/assertions/AC-binds with fresh identity.
5. `GET /atcs/[id]/usage` reports which tests chain this ATC (drives RESTRICT-delete messaging).

**Business rules**
- Layer is required and constrained to the CHECK set — a test must declare where it runs.
- Tags ≤10, each non-empty (CHECK).
- `atcs.status` is NOT settable by writers — it's a dead column; the business status of "does this ATC pass" comes from `run_atcs` verdicts (see flow 8).
- Deleting an ATC referenced by `test_steps` is rejected (`ON DELETE RESTRICT`) — usage check first.

**Code paths**: `app/api/v1/atcs/route.ts`, `atcs/[id]/route.ts`, `atcs/search/route.ts`, `atcs/[id]/usage/route.ts`, migrations 0087 (technique/priority), 0026/0030 (version/tags).

### 5. Module Tree Management

```
QA Engineer -> UI module panel -> POST /modules {projectId, parentId, name}
   -> RPC bunkai_create_module
      DB: depth(parent)+1 <= 6 else 45xxx (max-depth violation)
          materialized path updated; activity_log module.created
Rename/Move -> PATCH /modules/[id]
   -> RPC validates new depth for subtree; path rewrite
Archive -> DELETE (soft) -> modules.archived_at set, children hidden by default
```

1. Modules are created under a parent (`parentId = null` = root) via `POST /api/v1/projects/[id]/modules`.
2. The RPC computes subtree depth; exceeding 6 raises a domain error → `422`-family response.
3. Moves recompute the materialized path for the whole subtree atomically.
4. Archive is soft (`archived_at`); archived subtrees are excluded from pickers but retained for history/bug FKs.

**Business rules**
- Depth cap 6 is a product decision (UI navigability) enforced in DB, not UI.
- Deleting a module with active children/artifacts is blocked (FK RESTRICT on children); archive is the sanctioned retirement path.
- `module_id` on bugs is never null (always set at filing) — module history must remain answerable.

**Code paths**: `app/api/v1/projects/[id]/modules/route.ts`, `modules/[id]/route.ts`, module UI panels.

### 6. Acceptance Criteria Management

```
Dev/PO -> UI story drawer -> POST /user-stories/[id]/acceptance-criteria {text, position}
   -> RPC bunkai_create_ac
      DB: INSERT acceptance_criteria (position = append)
          IF story had 0 active ACs: story stays draft until >=1
   -> story marked ready_to_test only via explicit transition WITH >=1 active AC
Archive last AC -> DB trigger auto-reverts story -> draft
Link to ATC -> INSERT into atc_acceptance_criteria (M:N)
```

1. ACs are appended/inserted with explicit `position` inside their story (`POST /api/v1/user-stories/[id]/acceptance-criteria`).
2. `user_stories.status` moves `draft → ready_to_test` only through an explicit transition **and** only when ≥1 active AC exists (SQLSTATE 45xxx family otherwise).
3. Archiving an AC through `PATCH /api/v1/acceptance-criteria/[id]` fires the DB trigger: if it was the last active AC, the story reverts to `draft` automatically.
4. AC↔ATC bindings (`atc_acceptance_criteria`) are managed from the ATC side (flow 4) and surfaced by traceability reports (flow 16).

**Business rules**
- A story cannot enter `ready_to_test` with zero testable conditions.
- Archiving never destroys: `archived_at` only (0014 altered `archived_at` on modules/stories/ACs/atcs).
- Last-AC revert is DB-trigger-owned, so no code path can bypass it.

**Code paths**: `app/api/v1/user-stories/[id]/acceptance-criteria/route.ts`, `acceptance-criteria/[id]/route.ts`, migration 0014 + auto-revert trigger.

### 7. Test Authoring (chain, reorder, tags)

```
QA Engineer -> UI /tests/new -> POST /tests {title, atcIds[]}
   -> RPC bunkai_create_test
      DB: INSERT tests (version=1, tags default {})
          INSERT test_steps: position 1..n for each atcId (FK RESTRICT)
          activity_log test.created
   -> 201 + test JSON
Reorder -> POST /tests/[id]/reorder {orderedStepIds[]} (If-Match version)
   -> RPC rewrites positions 1..n in one txn; version+1
Tags    -> PATCH /tests/[id]/tags {tags[]} -> version+1
Edit ATC in chain -> allowed (same ATC twice = LEGAL, no unique(test,atc))
```

1. Creating a test = naming it + ordering existing ATCs (`POST /api/v1/tests`): the RPC inserts `tests` + N `test_steps` rows transactionally.
2. Reordering (`POST /api/v1/tests/[id]/reorder`) rewrites all positions in one transaction behind the `version` optimistic lock.
3. Tags are a `text[]` column (0030), trimmed/deduped app-side; title trimmed to 1–200 chars.
4. Deleting an ATC that sits in any chain is refused (`test_steps.atc_id → RESTRICT`) — the author must first remove it from the chain (`GET /atcs/[id]/usage` shows where).

**Business rules**
- A test is a *view over* ATCs, not a copy — chain edits are metadata-only; ATC content changes flow through automatically (why runs snapshot instead: see flow 8).
- The same ATC may appear at multiple positions (no uniqueness on `(test_id, atc_id)`) — used for repeat-verification scenarios.
- `tests` are workspace-scoped: they can reference ATCs from any project in the workspace (cross-project suites).

**Code paths**: `app/api/v1/tests/route.ts`, `tests/[id]/route.ts`, `tests/[id]/reorder/route.ts`, `tests/tags/route.ts`, `tests/search/route.ts`.

### 8. Test Run Execution (create → mark steps → finish/abort)

```
QA Engineer -> UI run wizard -> POST /runs {testId, startToken, envId?, via:'user'}
   -> RPC bunkai_create_run
      DB: idempotency: 24h window on (test_id, start_token) -> replay same run
          SNAPSHOT: test_steps -> run_steps (content copied),
                    per chain ATC -> run_atcs (verdict=pending)
          runs(status=running); activity_log run.started
      <- 201 + runId (replayed flag if duplicate)
   UI (Realtime on run_atcs/run_steps):
      POST /runs/[id]/steps/[stepId]/mark {status, note?, evidenceUrl?}
        -> RPC bunkai_mark_run_step (pending|passed|failed|blocked)
           -> recompute run_atcs verdict -> Realtime push -> UI updates live
   -> POST /runs/[id]/finish {verdict}
      -> RPC bunkai_finish_run (0067 +via): status passed|failed,
         remaining pending run_steps -> skipped; activity_log run.finished
         -> trigger activity_log_notify_run_event -> notifications
   OR -> POST /runs/[id]/abort {reason} -> status=aborted (45204/45206/45212
         terminal guards: first terminal wins, no un-terminal)
   OR -> pg_cron sweep (flow: Automatic processes) marks idle runs aborted via='sweep'
```

1. Start: `POST /api/v1/runs` with a client `startToken` — the RPC's 24h idempotency on `(test_id, start_token)` makes a retried create return the **same** run (idempotency_key family `452xx`).
2. Snapshot at creation: each chain `test_steps` row is copied into `run_steps` (content frozen) and each chain ATC gets a `run_atcs` shell with `verdict=pending`. Later ATC edits cannot rewrite this run.
3. Execution UI subscribes to Realtime (`run_atcs`, `run_steps` in `supabase_realtime` publication): each `POST /runs/[id]/steps/[stepId]/mark` updates one step and recomputes its `run_atcs` verdict (any `failed` → failed; any `blocked` → blocked; any `pending` → pending; else passed).
4. Completion: `POST /runs/[id]/finish {passed|failed}` flips `runs.status`, force-skips leftover `pending` run_steps → `skipped`, and appends `activity_log run.finished`.
5. The `activity_log_notify_run_event` trigger fans that out to in-app notifications for the workspace members entitled to run events (respecting `notification_preferences`).
6. Aborts: explicit user abort (`abort_reason`), or the **pg_cron sweep** aborting runs idle >4 minutes with `via='sweep'`.
7. Terminal guards (SQLSTATE 45204/45206/45212): once a run is terminal, every later finish/abort/mark is rejected — first terminal state wins.

**Business rules**
- Run history is immutable: snapshots + terminal guards mean metrics never drift after the fact.
- `startToken` idempotency exists because CLI/agents retry network calls — a retry must not spawn a second run.
- Only `runs` flagged with a `module_id` participate in module-scoped rollups; default runs are test-scoped.
- `via` distinguishes human-caused vs sweep-caused aborts for flake analytics (sweep aborts must not look like QA aborts).

**Code paths**: `app/api/v1/runs/route.ts`, `runs/[id]/route.ts`, `runs/[id]/finish/route.ts`, `runs/[id]/abort/route.ts`, `runs/[id]/steps/[stepId]/mark/route.ts`, `tests/[id]/runs/route.ts` (list, terminal-only), migrations 0031/0067/0075.

### 9. Bug Lifecycle (file → assign → transition)

```
QA (from failed run step) -> UI -> POST /bugs {title, severity P1-P4,
      moduleId, runId?, runStepId?, atcId?, evidenceUrls[]<=10}
   -> RPC bunkai_create_bug
      DB: status=open (entry only), title trimmed 5..200
          provenance FKs frozen-at-filing: run_id/run_step_id/atc_id
            ON DELETE SET NULL (module_id always set, cascade)
          bugs_check_consistency trigger (DEFINER) validates cross-refs
          activity_log bug.filed
      (bug.filed does NOT notify — run terminal event already did)
Assign -> POST /bugs/[id]/assign {assigneeUserId}
   -> RPC bunkai_assign_bug (self-assign allowed) -> activity_log bug.assigned
      -> trigger activity_log_notify_bug_event -> notifications (new assignee)
Transition -> POST /bugs/[id]/status {to}
   -> RPC bunkai_transition_bug_status: forward-ONLY single stage
      open -> in_progress -> resolved -> closed   (45311 = backward, 45310 = skip)
      -> activity_log bug.status_changed -> notifications (reporter+assignee)
Retest: resolved bug fails again -> QA reopens via forward path? NO:
   backward transitions are DB-blocked -> reopen = new bug linked by QA convention
```

1. Filing: from a failed `run_steps` row the UI pre-populates provenance; `POST /api/v1/bugs` → `bunkai_create_bug` inserts with `status=open` (the **only** entry point for status), title trimmed/validated 5–200, ≤10 evidence URLs.
2. Provenance rows (`run_id`, `run_step_id`, `atc_id`) are written once and marked `ON DELETE SET NULL`: if the upstream run/ATC is later purged, the bug keeps its module but loses the link (frozen semantics — no cascade that would orphan module attribution, no RESTRICT that would block cleanup).
3. Assignment (`POST /bugs/[id]/assign`) is RPC-mediated, emits `bug.assigned`, and the DB trigger notifies the new assignee (self-assign still notifies).
4. Status moves strictly forward one stage at a time: skipping (`45310`) and going backward (`45311`) are rejected by the RPC; `bug.status_changed` triggers notifications to reporter + assignee (minus the actor).
5. The `bugs_check_consistency` trigger (SECURITY DEFINER, 0054) is the backstop: it re-validates cross-references (e.g. provenance rows must belong to the bug's workspace/project scope) even if a write bypasses the RPC.

**Business rules**
- Severity is a product decision (`P1–P4`), set at filing and changeable through the transition RPC's audit trail.
- Provenance is evidence, not a live dependency — `SET NULL` preserves "we filed this from run X" until X is physically gone.
- No archive column: bugs are never hidden (0061) — "the bug table only grows" is the accepted model.
- Forward-only lifecycle means a fixed-then-reopened defect is a **new** bug (QA links them by convention) — deliberate choice to keep the state machine auditable.

**Code paths**: `app/api/v1/bugs/route.ts`, `bugs/[id]/route.ts`, `bugs/[id]/status/route.ts`, `bugs/[id]/assign/route.ts`, `projects/[id]/bugs/route.ts`, `projects/[id]/bugs/heatmap/route.ts`, migrations 0046/0051/0054/0061/0070.

### 10. Notifications Inbox & Preferences

```

                          | activity_log_notify_run_event

- Notifications are best-effort presentation of the audit trail, never a second source of truth (activity_log is).
- 90-day read visibility: older rows drop out of listing (storage hygiene), no hard delete.
- Idempotency at the DB level (source_event_id+recipient unique) is what makes trigger re-fires safe.

### 11. Daily Email Digest

```
Vercel Cron (0 8 * * * UTC, vercel.json)
   -> GET+POST /admin/send-digest (CRON_SECRET gate; both verbs, BK-882)
      -> RPC bunkai_notification_digest_candidates()  [service-role]
         DB: per user with unread notifs + email preference enabled:
             INSERT INTO notification_digest_log (user, day) status=pending
             ON CONFLICT DO NOTHING -> claim wins (cron retry safe)
      -> for each claimed row: TS groups + renders unread -> Resend send
         -> UPDATE digest_log status=sent|failed (+ error)
      -> activity not duplicated: digest reads notifications, never re-creates them
```

1. Vercel's cron hits `/api/v1/admin/send-digest` at 08:00 UTC; the route accepts GET *and* POST and authenticates with `CRON_SECRET` (both verbs because Vercel and manual probes differ — BK-882).
2. The candidates RPC claims one `notification_digest_log` row per user/day (`pending`, conflict → do-nothing): this is the claim ledger that makes cron retries harmless.
3. TypeScript groups the user's unread notifications, renders the email body, sends via **Resend**, then marks the claim `sent` or `failed` (with error text).
4. A crash between claim and send leaves `pending` rows — next day is a new row (per-day ledger), so at most a *delayed* digest, never a duplicate-day blast.

**Business rules**
- Digest is opt-out per `notification_preferences.email × event_type` — users who disabled email for a category don't get it in the digest either.
- Email sending lives in app code (Vercel), **not** Postgres: no DB egress capability by design.
- The digest is read-only over `notifications`; it creates no new notification rows.

**Code paths**: `vercel.json` (cron `0 8 * * *`), `app/api/v1/admin/send-digest/route.ts`, migration 0078, Resend client in `lib/`.

### 12. Billing Upgrade (Stripe Checkout → webhook → plan apply)

```
Owner -> UI settings/billing -> POST /workspaces/[id]/billing/checkout {seatQuantity}
   -> INSERT billing_checkout_sessions (status=open, target_plan='cloud',
         seat_quantity>0)   [partial unique: ONE open per workspace -> 409 if dup]
   -> create Stripe Checkout Session (client_reference_id = session row id)
   -> PATCH row with stripe_checkout_session_id
   -> 200 + checkoutUrl -> UI redirects to Stripe
Stripe -> POST /billing/webhook  (signature verified, raw body)
   -> INSERT stripe_webhook_events (PK=event id)  [replay -> conflict -> 200 no-op]
   -> for checkout.session.completed (paid):
        RPC bunkai_apply_billing_checkout_webhook_event
          workspaces.plan='cloud', purchased_seats=seat_quantity,
          checkout row status='completed'; activity_log workspace.plan_upgraded
   -> 200; Stripe retry-safe (event id fence + RPC idempotent)
Cancel -> POST /workspaces/[id]/billing/checkout/cancel
   -> open checkout row -> 'canceled' (does NOT touch plan)
```

1. The workspace **owner** opens billing settings; `POST /api/v1/workspaces/[id]/billing/checkout` inserts a `billing_checkout_sessions` row in `open` state. The partial unique index (`workspace_id WHERE status='open'`) enforces **one open attempt per workspace** — a second click returns `409`, not a second Stripe session.
2. The route creates the Stripe Checkout Session (plan `cloud`, seat quantity) and back-fills `stripe_checkout_session_id` (unique, nullable until then).
3. User pays on Stripe; Stripe calls `POST /api/v1/billing/webhook`. Signature verified against the raw body first.
4. The handler inserts the Stripe event id into `stripe_webhook_events` — **primary key conflict = duplicate delivery = immediate 200** (no reprocessing).
5. For a paid `checkout.session.completed`, the SECURITY DEFINER RPC applies the upgrade transactionally: `workspaces.plan='cloud'`, `purchased_seats=seat_quantity`, checkout row → `completed`, audit `workspace.plan_upgraded`.
6. The webhook path writes through the service-role client: `billing_checkout_sessions` and `stripe_webhook_events` have owner-SELECT-only / zero-policy RLS respectively — app code can read, only service-role/RPC can write.
7. Cancel path flips the open row to `canceled` without touching the plan.

**Business rules**
- Plans in play today: `community` (3 projects) → `cloud` (50 projects) → `enterprise` (unlimited); limits are SQL mirrors of `lib/billing/plan-tiers.ts` (0065) — **the DB is authoritative**.
- Seat count is *purchased* metadata (`purchased_seats`) — **invite-time seat enforcement does not exist yet** (follow-up ticket); limits currently gate projects, not members.
- No subscription lifecycle table yet (BK-231 pending): upgrade is a one-shot state change, not a recurring billing model.
- Webhook failure behavior: non-2xx → Stripe retries with backoff; the event-id fence makes retries safe; a lost event means plan not applied until manual backfill.

**Code paths**: `app/api/v1/workspaces/[id]/billing/route.ts`, `billing/checkout/route.ts`, `billing/checkout/cancel/route.ts`, `billing/webhook/route.ts`, `lib/billing/plan-tiers.ts`, migration 0077, `bunkai_apply_billing_checkout_webhook_event`.

### 14. Workspace Deletion, Restore & Purge

```
Owner -> DELETE /workspaces/[id] (owner only)
   -> RPC bunkai_request_workspace_deletion
      DB: workspaces.deleted_at = now()  (grace starts)
          revoke member PATs (access_tokens), revoke pending invites
          row_count_digest captured
          UPSERT workspace_deletions tombstone: purge_deadline = now()+30d
          activity_log workspace.deleted -> recipients list returned
   -> app-layer after(): Resend email to all members ("deleted, restore in 30d")
Restore (within grace) -> POST /workspaces/[id]/restore (or /restore route)
   -> RPC bunkai_restore_workspace_deletion: deleted_at=NULL, tombstone cleared
      -> activity_log workspace.restored
Purge (03:00 UTC pg_cron, bunkai-purge-deleted-workspaces)
   -> for workspaces where deleted_at + 30d <= now:
        DELETE workspaces -> CASCADE children
        workspace_deletions: purged_at=now(), purge_deadline kept (tombstone stays)
   -> RLS on workspace_deletions: ZERO policies -> only DEFINER RPCs touch it
```

1. Deletion is owner-only and **soft**: `bunkai_request_workspace_deletion` stamps `deleted_at`, revokes every member PAT and pending invite (revocation is part of the same RPC — no window where tokens outlive intent), captures a `row_count_digest`, and upserts the `workspace_deletions` tombstone with `purge_deadline = +30 days`.
2. The route's `after()` sends the courtesy email via **Resend** to all members (app-layer: Postgres cannot send email).
3. Restore exists for the whole 30-day window (`POST /api/v1/workspaces/[id]/restore`): clears `deleted_at` and the tombstone — business consequence: soft-delete is a recoverable mistake for 30 days, then irreversible.
4. At 03:00 UTC the pg_cron job `bunkai-purge-deleted-workspaces` hard-deletes expired tenants (`DELETE FROM workspaces` → CASCADE wipes projects/modules/stories/ATCs/runs/bugs…), then stamps `purged_at` on the tombstone — **the tombstone deliberately outlives the tenant** (it has no FK to workspaces).
5. `workspace_deletions` has RLS enabled with **zero policies**: no direct SQL access exists; only SECURITY DEFINER RPCs write it. There is **no status column** — state is derived (`purged_at IS NULL ? awaiting : purged`).

**Business rules**
- 30-day grace is the product promise (email says so); the cron is its executor.
- PAT/invite revocation happens at request time, not purge time — no authenticated traffic into a tenant pending death.
- The tombstone keeps `member_count` + `row_count_digest` for compliance ("what did this tenant contain?") after the rows are gone.
- No veto/approval flow: any owner deletion proceeds to purge unless restored (no admin hold observed — see gaps).

**Code paths**: `app/api/v1/workspaces/[id]/route.ts` (DELETE + after() email), `workspaces/[id]/restore/route.ts`, migrations 0084/0084a, pg_cron `bunkai-purge-deleted-workspaces`.

   open --(user/API cancel)-->  canceled
   open --(Stripe expire)-->     expired
   (partial unique: ONE open per workspace; completed/canceled/expired rows
    are historical and unlimited)
```

| From | To | Event | Effects |
|---|---|---|---|
| `open` | `completed` | Webhook `checkout.session.completed` (paid, event-id fenced) | `workspaces.plan='cloud'`, `purchased_seats` set, audit `workspace.plan_upgraded`. |
| `open` | `canceled` | `POST .../checkout/cancel` | Plan untouched. |
| `open` | `expired` | Stripe expiry | New checkout attempt allowed (freeing the one-open slot). |
| terminal | — | Second open attempt while one is `open` | **409** (partial unique) — prevents double Stripe sessions. |

### Workspace export status

```
   queued --> running --> completed (expires_at = completed_at + 168h)
                       \-> failed
```

| From | To | Event | Effects |
|---|---|---|---|
| `queued` | `running` | `after()` worker starts | Export row is the job queue (one active export enforced app-side). |
| `running` | `completed` | Archive built + uploaded to `workspace-exports` bucket | 7-day expiry armed; download RPC unlocks. |
| `running` | `failed` | Build/upload error | Error text stored; user may re-request (no auto-requeue). |
| `completed` | (expired) | `expires_at` passes | Download RPC refuses; archive reaped. |

### Workspace lifecycle (soft delete → purge / restore)

```
   active --DELETE (owner)--> soft-deleted (deleted_at set)
      soft-deleted --restore (<=30d)--> active (tombstone cleared)
      soft-deleted --cron 03:00 after 30d--> PURGED (rows CASCADE-deleted;
                                              tombstone purged_at stamped, STAYS)
```

| From | To | Event | Effects |
|---|---|---|---|
| `active` | soft-deleted | Owner `DELETE /workspaces/[id]` | PATs + invites revoked; `workspace_deletions.purge_deadline=+30d`; Resend notice to members. |
| soft-deleted | `active` | `POST /workspaces/[id]/restore` within grace | `deleted_at` cleared; tombstone removed; audit `workspace.restored`. |
| soft-deleted | purged | pg_cron `bunkai-purge-deleted-workspaces` (03:00 UTC) | `DELETE workspaces` → CASCADE all tenant rows; tombstone `purged_at` set (**tombstone outlives tenant**). |

### Notification read state

```
   unread (read_at IS NULL) --PUT /read | /read-all--> read
```

| From | To | Event | Effects |
|---|---|---|---|
| unread | read | User marks read | `read_at` set; unread_count recomputed; 90-day visibility window still applies. |

### Email digest claim

```
   pending --(send ok)--> sent
   pending --(send err)--> failed   (error text stored)
   (one row per user per calendar day; conflict -> no new claim)
```

| From | To | Event | Effects |
|---|---|---|---|
| — | `pending` | Cron candidates RPC (ON CONFLICT DO NOTHING) | Claim = duplicate-blast protection. |
| `pending` | `sent`/`failed` | Resend attempt in route | `failed` rows are visible for ops; next digest is a **new day's row** (no same-day retry storm). |

## External Integrations

### Supabase (Postgres + Auth + Storage + Realtime)

```
Next.js route handler
   |-- session path: RLS-scoped client (policy evaluates request.jwt)
   |-- PAT/privileged path: service-role or SECURITY DEFINER RPC
   |      (actor bound server-side, ADR-0012 — never client-supplied)
   v
Postgres: RLS on every tenant table + ~110 bunkai_* RPCs
   |-- Storage bucket 'workspace-exports'  <- export archives (168h)
   |-- Realtime publication: run_atcs, run_steps, notifications
   +-- pg_cron: sweep + purge jobs
```

- **Data**: all tenant state; **RLS is the authorization source of truth** (app checks are advisory).
- **Dependent flows**: every flow in this document; runs' live UI depends on Realtime (`run_atcs`/`run_steps`), inbox badge on `notifications`.
- **Failure behavior**: DB down → all writes fail closed (5xx); no partial-apply risk because mutations are RPC transactions. Realtime loss → UI shows stale verdicts until reconnect (business tolerates — DB is correct).
- **QA access**: dedicated read-only role `qa_inspector_ro` (BYPASSRLS-adjacent grants) exists for DBHub MCP analysis; 0086 revoked secret-table access from it; **4 pre-existing GRANT offenders on that role remain** (see gaps).

### Jira (Cloud)

```
Import worker (after()) --email+APIToken--> api.atlassian.com (JQL search)
      |                                         |
      +---- upsert user_stories/acceptance_criteria (no reverse sync)
Read-only from Bunkai's perspective: no webhooks IN, no status pushes OUT.
```

- **Data**: issues → stories + ACs (one-way).
- **Dependent flows**: Flow 3 (import); module mapping rules decide placement.
- **Failure**: auth error / JQL error → `import_jobs.status='failed'`, partial rows kept, user re-runs (upsert = safe re-entry).

### Stripe

```
UI billing settings -> POST checkout -> Stripe Checkout (hosted page)
                              |                 |
                              |    user pays    |
                              |                 v
                              +---- POST /api/v1/billing/webhook
                                     (HMAC signature, raw body)
                                     -> stripe_webhook_events (PK fence)
                                     -> plan cloud + seats (service-role RPC)
```

- **Data**: plan state (`community→cloud`), `purchased_seats`; checkout attempt rows.
- **Dependent flows**: Flow 12; project-limit trigger switches 3→50 on plan flip.
- **Failure**: webhook non-2xx → Stripe retries (fence = idempotent); signature mismatch → rejected (no state change); lost event → plan not applied (manual backfill needed — no poller exists).

### Resend (email)

```
[Digest route, 08:00]  ---> Resend API ---> member inbox (daily unread digest)
[Deletion route, on request] --> Resend API ---> member inbox (grace notice)
All sending in APP CODE; no DB egress by design.
```

- **Data**: rendered digest bodies; deletion notices. No templates DB-side.
- **Dependent flows**: Flow 11 (digest), Flow 14 (deletion notice).
- **Failure**: Resend outage → digest claim marked `failed` (row retained, no same-day retry storm); deletion email lost but tombstone/restore path unaffected (email is courtesy, not mechanism).

### Vercel (platform: hosting + cron + workers)

```
GitHub push -> Vercel build -> Next.js app (routes + after() workers)
vercel.json cron: 0 8 * * * GET /admin/send-digest (CRON_SECRET)
after(): import runner | export builder | deletion email
```

- **Data**: none of its own; executes app logic and schedules it.
- **Dependent flows**: 3 (import), 11 (digest), 13 (export), 14 (email).
- **Failure**: cron misconfigured/removed → digest silently stops (claim rows simply don't appear); `after()` lost on cold-crash → export stuck `running` / import stuck `running` (status columns are the observable signal).
